# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`aoa` is a prototype of an "always-on" agent (Python ≥3.11, Anthropic SDK, Temporal, FastAPI, SQLite). `README.md` has a table mapping each architecture idea to the file that implements it, plus an "Honest limits" section. Read both before changing behavior. Default models: `claude-sonnet-5-5` (main/helper), `claude-haiku-5-5` (command reviewer). There is no linter or formatter configured.

## Commands

```bash
python -m venv .venv && . .venv/bin/activate && pip install -e '.[dev]'

pytest                                   # fast suite: scripted FakeLLM, no server, no API key
pytest tests/test_units.py::test_name    # single test (asyncio_mode=auto, so plain `async def` tests work)
pytest -m temporal                       # end-to-end; needs `temporal server start-dev` (skips otherwise)

# full stack (four terminals; needs ANTHROPIC_API_KEY)
temporal server start-dev
python -m aoa.worker
uvicorn aoa.server:app --port 8000
python -m aoa.client_cli --session main
```

**Running for real (local, always-on):** the four services run as launchd user agents (`com.aoa.temporal|worker|server|slack-bridge`, installed by `deploy/install-launchd.sh install`, KeepAlive, logs in `data/logs/`, Temporal history in `data/temporal.db`). They run whatever is checked out in this repo, so after changing code on `main` restart the affected service: `launchctl kickstart -k gui/$(id -u)/com.aoa.worker` (same for `server`, `slack-bridge`). Do not start hand-run copies alongside them (ports 7233/8000). Status: `deploy/install-launchd.sh status`. An activity's result shape change must stay replay-compatible with in-flight workflows (see `GithubPollWorkflow`).

`python -m aoa usage [--days N]` prints estimated spend per day and per source from the `usage` table (list prices in `aoa/pricing.py`, dated; update them when prices change; live services only, evals are not in it).

All configuration is env vars read in `aoa/config.py` (`Settings.from_env`, all prefixed `AOA_`). Tests redirect state with `AOA_DATA_DIR` (see the `settings` fixture in `tests/conftest.py`).

## Architecture

The key design: **the agent logic is written once as `AgentCore` methods and driven by two interchangeable runners.**

- `core.py` — `AgentCore`: every durable step (`prepare_turn`, `llm_step`, `run_tool`, `append_results`, `maybe_compact`, `warm_cache`, ...) as a plain async method. All state-changing steps are idempotent through `Store.commit_step` / `step_get` keyed by a step key, so a retried activity returns the stored result instead of redoing work.
- `loop.py` — `run_agent_loop`: the model→tools loop. It does **no I/O** (it must stay deterministic because it runs inside a Temporal workflow) and talks to the world only through the `Ops` protocol. Don't add clocks, randomness, or I/O here.
- Two `Ops` implementations: `workflows.WorkflowOps` (each op is a Temporal activity or child workflow; wired to `core` via `activities.py`) and `direct.DirectOps` (plain in-process calls, used by most tests and usable without a server).
- `workflows.py` — `SessionWorkflow` (one long-lived workflow per session: user/background queues, batch window, idle→sandbox sleep, cache warming, continue-as-new), `HelperWorkflow` (child workflow for `spawn_helper`, fresh conversation), `RoutineWorkflow` (fired by Temporal Schedules). Workflow code must stay deterministic; config arrives as workflow input (`cfg` dict), not via `Settings`.
- `store.py` — single SQLite file (WAL) shared by all workers: messages, step idempotency records, event dedupe, client outbox, usage, approvals, routines, kv. Temporal history carries orchestration only; conversation data lives here.
- Event path: `server.py` webhooks (untrusted) / client / routines → `delivery.py` signal-with-start → `SessionWorkflow.submit_event` (priority 0 = user, preempts and is steered into the in-flight step via `append_results`).

Things that are easy to break:

- **Workflow changes must stay replay-compatible.** `SessionWorkflow` runs for days and PR workflows run across deploys, so any change to the commands a workflow issues (a new activity, timer, child start, reordering) needs a `workflow.patched("name")` guard. `tests/test_replay.py` replays the recorded histories in `tests/histories/` (including two recorded by an older worker) and fails if a change would break them; never re-record a history to make it pass. Add a scenario to `tests/histories/capture.py` when you add a new workflow path (needs the local Temporal server). PR workflows carry search attributes `Repo`, `PrNumber`, `Sha`, `Session` (registered by `search_attrs.ensure_registered` at worker and server start): `temporal workflow list --query 'PrNumber=27'`.
- **Tools run at most once** (`NO_RETRY` in `WorkflowOps.run_tool`); a failed tool is reported to the model as "effects unknown", never re-run. Model calls are retried. Keep new tool handlers consistent with this.
- **Prompt-cache stability** (`prompt.py`, `llm.place_cache_breakpoints`): the system prompt and tool block must be a fixed, ordered prefix; volatile context (time, scratchpad, recent log) goes into the new user message via `volatile_context_block`, not the system prompt. `core.llm_step` logs a warning on a cache miss within the TTL, which is treated as a bug. `AOA_CACHE_TTL` (300 or 3600; normalised in `Settings`) sets the `cache_control` ttl on every breakpoint via `llm.place_cache_breakpoints`, and the warm-up and compaction windows follow it; the default stays 5m because 1h costs more at this agent's call spacing (see `.env.example`). Compaction and `warm_cache` deliberately reuse the exact main-agent prefix via `_setup("main", 0)`. Model responses keep `thinking` / `redacted_thinking` blocks verbatim (the API rejects a changed or reordered one, and a breakpoint must never land on one); Where the code parses model JSON it asks the API to enforce a schema (`output_config.format`, `create(..., output_format=)`): the command reviewer (`safety.REVIEW_SCHEMA`) and the PR-review conversations (`pr_review.VERDICT_SCHEMA`, applied by `core._output_for`); a schema the API rejects is retried once without it and the tolerant parsers still validate. Native server-side tool search was evaluated and not adopted (#38: ~730 deferred-tool tokens, far below its intended scale). `AOA_REVIEW_THINKING` (an effort level, off by default) turns on adaptive thinking for the PR-review helper conversations (`prreview/...`) only. The current models reject `thinking.type=enabled` with a budget.
- **Tools** (`tools.py`): core tools ship full schemas; deferred tools appear only by name in the prompt and are reached via `tool_search` / `call_deferred`. `spawn_helper` is declared in `tools.py` but executed by the loop, not a handler. Handlers raise `ToolError` with an actionable message for the model; results over `tool_result_max_chars` are spilled to a sandbox file by `core._cap`.
- **Trust**: external event text is rendered/wrapped as untrusted data (`events.render_event_text`, `safety.wrap_untrusted`); commands pass a denylist then a reviewer model that fails closed (`safety.py`); `external_send` goes through the approval flow (a pending approval gets one nudge after `AOA_APPROVAL_NUDGE`, default 4h, and expires after `AOA_APPROVAL_EXPIRE`, default 24h, driven by `SessionWorkflow` timers guarded by `workflow.patched("approval-expiry")`; an expired approval cannot be approved late); only user-started turns (`trigger_user`) may create routines, and `send_user` turns an `update` into a `reply` in those turns so quiet hours never hold an answer. `publish_pr_review` checks each finding against the PR diff (`pr_review.check_citations`: a file or line the diff does not show is removed from a finding, which is always kept, and the verdict never changes; skipped if the head moved or the diff is unavailable). The owner's per-repo notes come from `<data_dir>/review-focus/<owner>__<repo>.md` (a local file, never read from the PR). PR reviews post as a real APPROVE / REQUEST_CHANGES only through the reviewer identity (`gh_reviewer.py`: `AOA_REVIEWER_APP_ID` + key file, or `AOA_REVIEWER_TOKEN`; off when unset), falling back to a comment review on any failure. Merging a PR is never a model tool: only a Slack [Merge] click on an approved review card (an opaque offer id stored by `publish_pr_review`) starts `MergePrWorkflow`, which pins the reviewed commit. On conflicts it resolves them in a temp clone and pushes (`pr_resolve.py`; token only via `GIT_CONFIG_*` env, tests run with an allowlisted env), and the new commit needs its own review and click. It refuses while GitHub auto-merge is on (checked before cloning and again before the push), never pushes a clean merge (`no_conflict`: GitHub's status was stale), and requires every line outside the conflict hunks to survive verbatim (`finish_resolution`). Failure `action`s in `pr_merge.RETRYABLE` bring the card's Merge button back; `needs_human`, `stale` and `tests_failed` do not. Per-repo test command: `AOA_TEST_COMMANDS` > `.aoa/test-command` as it is on the base branch (never the PR's) > pytest in a fresh venv. Those tests run as your user, not in a container (#21 was skipped on purpose), so the resolver is for your own PRs only.
- `notify.Notifier` decides whether outbound messages go now or are held in a digest (min interval, quiet hours); replies/questions/approvals/urgent always go. Held updates are delivered by a durable timer: `SessionWorkflow` asks `digest_status` for `Notifier.next_flush_at` after each turn and wakes at that time to run `flush_digest` (idempotent client key; guarded by `workflow.patched("digest-flush")`).
- `sandbox.LocalSandbox` is not isolation (runs as your user in a directory); `memory.py` is file-based (profile, dated log, scratchpad, skills) under `<data_dir>/memory`.

## Testing

`aoa/testing.py` (shipped in the package) provides `FakeLLM` (scripted responses; helpers `text()` and `tool()`; a step may be content blocks, a callable, or an Exception) and `MemoryScheduler`. `tests/conftest.py`'s `make_core(script)` builds an `AgentCore` with a fixed clock (2026-10-14 14:00 New York) and returns `(core, llm)`; `bg_event` / `usr_event` build event dicts. Prefer testing through `direct.handle_events` rather than needing Temporal; reserve `@pytest.mark.temporal` for workflow-specific behavior (`tests/test_temporal_e2e.py`).

## Evals

`python -m evals [--runs N] [--case NAME] [--batch] [--list]` runs the seed behavior suite against the **real model** (needs `ANTHROPIC_API_KEY`; export only that, not the GitHub token). Each run uses a throwaway data dir, an in-memory scheduler and a fake GitHub (`gh_call` replaced by a recorder); `external_send` is already a stub. Cases (`evals/cases.py`) are `hard` (safety rules, must pass every run; non-zero exit otherwise) or `soft` (policy; watch the pass rate). Graders (`evals/graders.py`) are deterministic Python over the run's outbox, tool calls and recorded effects; they have canned-run unit tests in `tests/test_evals.py` (default `pytest`, no model). Results go to `evals/results/*.json` (git-ignored). Cost: the full suite at 3 runs/case (30 runs) used about 0.28M cache-read, 7k cache-write, 10k output tokens and took ~45 s, because runs share the cached prompt prefix; a cold cache costs more. `--batch` sends each round of model calls through the Message Batches API (`batch_llm.py`: all runs' next calls go out as one batch, the coordinator polls until it ends): half price but minutes per round, for large `--runs`. **Hard review set:** `python -m evals --tag review-hard` (cases tagged `slow` are left out of a default run). Ten PR diffs from this repo's own history (`evals/review_fixtures/`, rebuilt by `python -m evals.review_fixtures.build`): six at a commit whose review found real problems that were then fixed (the reviewer should name them; `finds_defects` records `found/total` per run in the results), and four fixed commits the reviewer approved (no high finding, approving verdict). Needles are loose keyword alternatives, so a miss can be wording: read `findings` in the results JSON before blaming the reviewer. Use it as the baseline before changing the reviewer (a verification pass, a model tier). Cost of 30 runs: about 5.5M cache-read, 0.64M cache-write and 0.14M output tokens, ~9 min.
`--second-pass` is an experiment flag (evals only, not in the product): it reviews each PR twice, the second pass hunting ordering, error-path and cross-file bugs, and merges the findings.
Add a case whenever a behavior is verified by hand or a bug is found.

## Pull requests

Link every PR to the issue it addresses with a closing keyword in the body (`Closes #N`, `Fixes #N`), so merging closes the issue automatically. If there is no issue, create one first. Use `Refs #N` only when the PR intentionally leaves the issue open. Keywords only fire when the PR merges into the default branch. `.github/pull_request_template.md` has the skeleton.
